# tests/a-lightning-wait-is-judged-against-the-pool-that-could-end-it.law.test.ts

lightning_alerts paged LIGHTNING_LATENCY_REGRESSION all day on 2026-11-19 for the idle_to_match and fast_fold_to_next_hand legs of Lightning clusters whose pool was thin, such as NLH 1.00/2.00 Lightning Games (563279fc). That cluster held 4 to 8 players for 72 hours, so it paged nearly every hour. A wait for a new table depends on how many players can end it. Measured over 72 hours across eight clusters, the median idle_to_match p95 was 13 to 20 s with fewer than 9 players held and 3.9 s with 16 to 24 held. The 5,000 ms ceiling is meant for a full pool. This law pins the repair. The four wait legs are judged only when every window under judgement held the minimum pool through it: three rings of the cluster's handedness, or the cluster's own `alert_latency_wait_min_pool`, where 0 restores the old rule. The four server legs are judged as before, at any pool size. A full pool that still waits past the ceiling still pages, with each window's pool in the alert context. The migration proves the thin-pool, full-pool and server-leg cases on fixture windows before COMMIT.
