# tests/the-post-seal-backup-certifies-the-next-candidate.law.test.ts

The Backup run that answers a seal certifies the next candidate, not the build that just sealed, and one schema-evidence drift during the export costs one bounded re-export instead of the cycle (2026-11-24, O24). The post-seal run used to hold the one Backup host for about 48 minutes re-certifying the serving build (45370915542, 45399317563), a certificate the selector never reads, so each three-hour cycle had one attempt. The law pins that after the unchanged custody proof the plan job's `next` step targets the newest first-parent commit of the run's own commit touching `server/` or a `CONTROL_INPUTS` path when it is ahead of the sealed build, never retargets the control, plans nothing (no host, no status) when nothing is ahead, certifies the sealed build as before when unreadable, and lets the freeze baseline reader alone decide inside tonight's certification window; that a next-candidate run waits at most 25 minutes inside the one existing `refresh-due` read, hands the host back on a still-uninstalled migration or on a standing success for production's current set rehearsed against the sealed build, and follows the push rules for late supersession and the mid-soak yield; that the export step repeats exactly once after a fixed 45 second pause only when the offline evidence comparison refuses; and that no timer or `workflow_run` trigger is added.
