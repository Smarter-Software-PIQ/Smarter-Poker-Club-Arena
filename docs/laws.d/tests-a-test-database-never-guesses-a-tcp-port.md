# tests/a-test-database-never-guesses-a-tcp-port.law.test.ts

A `scripts/ci` Python harness that makes PostgreSQL listen on TCP takes its port from the kernel (`bind`/`getsockname`), never from the process id or a literal inside Linux's ephemeral range, where an outbound connection on the runner can already own it. The twelve harnesses whose clients all use their own Unix socket listen on no TCP address (`-c listen_addresses=`) and print the server log when `pg_ctl` fails; the TLS credential check, which needs TCP, asks the kernel for its port and passes it to its fixture. Three accounting shards had failed with a bare "pg_ctl: could not start server" between 2026-11-05 and 2026-11-07. The same holds for every vitest test under `tests/` (2026-11-24): twelve `tests/unit` Postgres tests drew a port from `20000 + random * 30000` and listened on 127.0.0.1, and PR #11911's first run lost `playedHeadsUpClubRetirement.pg.test.ts` to "could not start server" in 1.5 s with no server log. No file under `tests/` that runs `pg_ctl` may listen on TCP, set PGHOST to a loopback address or compute a port from `Math.random`; the twelve use `tests/helpers/scratchPostgres.ts`, which listens on a socket in a directory of the test's own and appends the server log to a failed start.
