# server/src/testing/theServerSuiteAssertsNoTightWallClockBound.law.test.ts

A server test does not hold a tight absolute upper bound on real elapsed time. The Server Engine shards are required checks and the engine prequalification runs them on the exact commit of every release candidate, so `expect(elapsedMs).toBeLessThan(25)` decides a merge or a three-hour release cycle by how busy a shared runner was (PR #11910, run 45375939160: 29.08 ms against 25 on unchanged code, green on rerun). The law reads every test file under `server/src` (`wallClockBoundSurvey.ts`) and fails on an upper bound under 1,000 ms on a value measured with `performance.now()`, `Date.now()` or `process.hrtime`, unless the test runs under a fake or stubbed clock, the bound is itself measured in the same test, or the value is the `ratio` of `measureRelativeCost` (`server/src/testing/relativeCost.ts`: subject and reference timed in alternating rounds in one process, fastest round of each). Bounds that predate the law are named one by one in `KNOWN` with a reason, as `hang` (a ceiling whose real size is seconds) or `debt` (a tight bound not yet converted); an entry that matches nothing fails the law, so the list only shrinks. The survey follows a value only where the file shows the clock being read and subtracted; an elapsed value that arrives through an imported helper or an object field is outside it.
