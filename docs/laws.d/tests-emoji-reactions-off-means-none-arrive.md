# tests/emoji-reactions-off-means-none-arrive.law.test.tsx

The Emoji Reactions switch in Table Settings is a RECEIVE gate, not only a send gate (Dan 2026-11-12: "IF A USER WANTS TO TURN THEM OFF AND NOT SEE IT, THEY SHOULD JUST TURN OFF, BUT THE BUTTON DOESN'T SEEM TO WORK, IT'S SILENTLY FAILING"), because `emoji_enabled` used to gate only the throwable selector, the Hero Hub throwables tab and the TableReactions overlay while `parseIncomingMessage` in `useTableChat` — the single inbound door for both `[REACTION:...]` and `[THROW:...]` — read nothing at all, so a player who switched it off lost the ability to send one and kept watching every throwable in the room land on their felt; the law pins that an incoming reaction and an incoming throwable are both consumed and dropped while the setting is off (consumed, so the raw wire text never leaks into the chat feed as an ordinary message), that both still arrive while it is on, that a caller passing no gate is never silently muted, that the gate is read at message-delivery time so a mid-session flip is live rather than frozen at table-join time, and that TablePage keeps feeding the live setting into that gate and keeps the render-side fail-safe that hands `ThrowAnimationContainer` an empty list and drains the playback queue instead of unmounting it. The law also pins the sibling: Text Messages, the only other table setting with a network receive side, keeps its one derived gate (socialFeaturesAllowed) over the chat sheet, seat speech bubbles and voice bubbles, so that switch can never drift into the same send-gated-but-receive-ungated shape.
