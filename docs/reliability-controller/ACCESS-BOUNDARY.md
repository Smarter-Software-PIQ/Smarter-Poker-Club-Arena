# Reliability Controller Stage B: Access Boundary

Written 2026-11-10 (UTC) for migration `20261110000020_reliability_controller_stage_b.sql`. "Test" means a behaviour of `scripts/ci/test-reliability-controller-stage-b.py` (PostgreSQL 17 fixture, `SET ROLE`); it is not proof of production wiring (see `FIXTURE-PARITY.md`).

## 1. What Production Says (read-only, 2026-11-10)

- `pg_default_acl` holds no entry for schema `smarter_private` and no database-wide entry that covers it. A new table or sequence there is owner-only; a new function gets PostgreSQL's built-in `EXECUTE` to `PUBLIC`. The three newest existing functions in the schema carry `{postgres=X/postgres}` and the three newest tables `{postgres=arwdDxtm/postgres}`: each was revoked by its own migration. This migration does the same, by name, for every object.
- `anon`, `authenticated` and `service_role` hold `USAGE` on `smarter_private`, so schema usage is not a boundary; object privileges are.
- `public.operational_alert_events`: `{postgres=arwdDxtm, service_role=arwdDxtm}`. `public.fn_record_operational_alert`: SECURITY INVOKER, `EXECUTE` for `postgres` and `service_role` only. So the inbox is written by `service_role` (World Hub through PostgREST) and by `postgres` (pg_cron jobs and SECURITY DEFINER producers such as `fn_ca_table_stall_watch_ingest`, `fn_ca_engine_cutover_watch`, `fn_ca_daily_window_lobby_close_page`). No browser role can write it.
- Every `cron.job` row runs as `postgres` in database `postgres`.

## 3. Why Each Entry Point Is SECURITY DEFINER

All six have `search_path = pg_catalog, smarter_private` and name every other object with its schema.

| Function                                   | Why definer                                                                                                                                                                                   |
| ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `reliability_trg_operational_alert_intake` | The inbox row is written by `service_role` or `postgres`; the controller tables grant `service_role` SELECT only, so intake must run as the owner                                             |
| `reliability_tick`                         | `service_role` may run it on demand and has no write privilege on the tables; it also refuses any JWT role other than `service_role`                                                          |
| `reliability_deliver_notifications`        | Writes `public.social_*`, `public.push_outbox` and the outbox as the owner; refuses any JWT role other than `service_role`                                                                    |
| `reliability_transition`                   | Updates `reliability_incidents` and appends history for a `service_role` operator; it carries no caller check because intake reaches it under the inbox writer's role, so EXECUTE is the gate |
| `reliability_send_validation_message`      | Enqueues and delivers one message for `service_role`                                                                                                                                          |
| `public.fn_reliability_incident_for_owner` | The only browser surface; reads tables `authenticated` cannot read, after `fn_is_platform_alert_recipient(auth.uid())`                                                                        |

## 4. Result

Every authorized caller worked as written; no grant had to be changed. One addition: the four identity sequences are now revoked by name beside `reliability_notifications_id_seq` (they were already owner-only by default).

Not proven here: the fixture's `postgres` is a superuser and production's is not (it is the object owner, which is what the privileges above rely on); a real PostgREST request; pg_cron actually executing the job.
