# Incident Class Catalog (Reliability Controller)

Written 2026-11-09 (UTC). Built only from `SOURCE-INVENTORY.md` (rules, inbox names, producer verification in its section 3a) and `RECOVERY-OWNERSHIP-MAP.md` (existing recovery actors), plus the repo files named below. Paths are relative to the Club Arena repo; `S/` = `server/src/`; rule files are in `infra/monitoring/`. Where evidence is missing the cell says "unknown".

This document grants no recovery action to any class. The only permitted controller actions are "detect and escalate" and, for money, "detect, link to authoritative incident, escalate".

## 3. Never

The controller never does any of the following, for any class:

| Never                                                                                                        | Owner that already exists                                                                                                    |
| ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Whole-engine restart, stop or start                                                                          | Docker restart policy (`server/scripts/engine-up.sh:460`) and `sp-autoheal` (`infra/monitoring/autoheal-compose.yml`) own it |
| Releases (stage, cutover, rollback, dispatching a workflow, calling `/internal/maintenance-recovery-window`) | `engine-release-transaction.sh`, `engine-release-recover.sh` and the release workflows                                       |
| Tournament start holds                                                                                       | Owner only (`docs/agent-policy/OWNER-POLICY.md:17-19`)                                                                       |
| Money adjustments (ledger, wallet, payout, settlement replay, outbox replay)                                 | Settlement paths and the manual adjustment functions `fn_ca_propose_manual_adjustment` / `fn_ca_approve_manual_adjustment`   |
| Closing `financial_alerts` or `ca_drift_incidents` rows                                                      | Their producers and the four auto-resolve jobs listed in the ownership map section 1d                                        |

## 7. Hold-Down (2026-11-11, migration `20261111222330`)

Section 6 flagged two flapping names that the class model could not tune. A class row now carries a hold-down, and both names have one.

| Column                 | Meaning                                                                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------- |
| `hold_down_seconds`    | The incident escalates only after staying firing this long. Every resolve resets the clock.       |
| `hold_down_flaps`      | Or after this many firing episodes inside `hold_down_flap_window_seconds`.                        |
| `quiet_window_seconds` | A resolved incident must stay quiet this long before it is recovered. Default 1800 for every row. |

Where it runs: intake (`reliability_apply_signal` reads the class row the delivery matched, stamps `class_rule_id` and `firing_since` on the incident, then escalates or records a `hold_down` event) and the transition (`reliability_transition` clears `firing_since` on leaving the firing statuses). The existing `reliability_tick` steps 1 and 3 read the same row, so a held incident that keeps firing with no further delivery still escalates. No job was added. A row without `hold_down_seconds` keeps the Stage B rule exactly (native test).
