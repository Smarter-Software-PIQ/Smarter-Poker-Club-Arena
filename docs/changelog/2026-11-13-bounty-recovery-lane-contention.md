# Bounty recovery admits an available settlement lane

Incident `2b26f12f-bc94-4236-a95c-09bb08a4fe26` fired after repeated recovery RPC statement timeouts. Production PostgreSQL contexts show five calls waiting on the per-tournament advisory settlement lane and one payment timing out in a wallet notification. Mystery award `80eba841-8972-4b01-8f95-5b438d5f5c67` subsequently completed; its obligation settled at 05:25:40 UTC. No manual settlement or wallet changes were performed. The alert sent a resolved signal at 05:36:33 UTC. That signal alone does not prove durable recovery.

The recovery function previously selected the oldest due tournament and waited on its exclusive lane. Independent obligations could not progress during that wait. It now tries the existing global shared lock followed by each due tournament lane until one is available, selecting one available event. Busy/global-terminal contention returns the existing pending and due-time contract to the causal drain. It never releases another transaction's lock or claims an unpaid obligation. Canonical payment, generation ordering, complete-marker verification, transaction custody and permissions remain unchanged.

The first protected installation refused the change because the MTT admission contract still pinned the old sweep definition. Nothing committed. The successor rotates exactly that prepared pin to the new catalog definition in the same transaction, preserving every other prepared value and the guard's full metadata and executable source. No stale-pin exception or admission ABI change is used.

A native PostgreSQL regression uses independent sessions to reproduce the original timeout, then verifies independent event progress, explicit scope, global terminal and shared-hand exclusion, retained pending obligations, more than twenty busy events, and duplicate no-op. The actual applier stale-pin wrapper reproduces the refused installation, proves rollback on a wrong pin, and accepts the atomic correction. The captured production guard also passes this rehearsal. The unit suite invokes the retained regression directly. A separate source assertion proves the settlement body after admission is unchanged. The underlying wallet timeout is not attributed to the roster query: its direct read-only plan was 0.194 ms. This correction addresses the demonstrated recovery admission failure; it does not claim every database timeout is impossible.

Protected merge, exact migration installation and live alert/obligation verification remain required. No engine replacement is needed.
