# The shadow stage's latency breaker charges the time a re-decision ran (2026-11-23)

The shadow stage's breaker (`OptionShadowStageGuard`, `HorseOptionShadowStage.ts`) now judges each staged re-decision by the smaller of its wall time and the worker thread's own CPU time over the same span (`optionShadowStageChargedMs`, read with `process.threadCpuUsage`). The rules are unchanged: one re-decision over 150 ms, or three over 50 ms in the last 20, stops that option in that worker until it restarts.

- **Why.** The breaker read wall time only, so a pause of the worker thread during a re-decision was charged to the option. Serving `735299cd5fda` on 2026-11-23, `omahaMathCorePlo5Flop` re-decided 727 times (avg 17.0 ms) and one re-decision of 195.8 ms tripped the breaker on worker `78ffa527` at about 07:22Z, while that worker's 48 acted decisions of the same minute took at most 41.4 ms. Five of the 727 took 100-200 ms (0.69%), against 80 of 137,292 acted decisions (0.058%) on the engine's eight workers in the same window, and none of those five minutes had an acted decision on the same worker over 78 ms. On 2026-11-22 at 19:32Z (`ea92b56f`) `omahaStabDefenceIsPriced`, whose re-decisions take 1.4-6.4 ms, tripped it at 392.2 ms.
- **The pricer's own cost.** On the Mac (origin/main `608f33c5`, Node 22.23.3, 10,000 PLO5 flop decisions with the core on, 624 recorded and generated states, varied seeds, twice): thread CPU p50 7.1 / p95 10.6-10.7 / p99 13.2 / p99.9 18.7-19.2 ms; once warm, at most 27.5 ms. The only CPU readings over 40 ms were the first decision or two of each process (66-68 ms). Wall-clock readings over 50 ms (146.1, 81.2, 64.9 ms) had 8-28 ms of CPU behind them. The Mac is about 2-3x faster than an engine vCPU.
- **Not weaker.** The charge is never above the wall time, so the breaker trips nowhere it did not trip before. A re-decision that is slow because it computes is on the CPU for that time and trips at the same re-decision as before. With no CPU reading (a runtime without `threadCpuUsage`, or a failed read) the charge is the wall time, exactly as before. What is no longer charged: time the thread did not run (descheduled, or blocked in a synchronous wait). The staged decide path does no synchronous I/O.
- **Telemetry.** New latency scope `option_shadow_stage_redecide_cpu` (the thread CPU of each staged re-decision) beside `option_shadow_stage_redecide` (wall, unchanged), and counter `option_shadow_stage_wall_only_slow_seen` for a re-decision whose wall time alone would have been over 50 ms and whose charged time is not.
- **Unchanged.** Acted decisions, the inline option shadow and the style shadow (no CPU read, no breaker), the 50 ms acted-time budget, the Horse-only cap, the per-minute budget, the receipts. The change applies to every staged option alike, because the same reasoning holds for each: the breaker exists to stop an option whose re-decisions are costly, and a pause of the thread is not a cost of the option.
- **Proof.** `aListedOptionInShadowStageNeverChangesTheActedDecision.test.ts`: the charge is min(wall, CPU) and never above the wall time; over 400 seeded streams an option whose CPU is its wall time trips at the same re-decision as the wall-time breaker, and with any CPU reading the breaker never trips where, or earlier than, the wall-time one; through the worker with the live CPU clock, a re-decision blocked 165 ms does not trip and the next three are re-decided, one that computes for 165 ms trips exactly as before, with no CPU reading the blocked one trips as before; the CPU clock is read only around a staged re-decision and the acted decisions are those of no row.
