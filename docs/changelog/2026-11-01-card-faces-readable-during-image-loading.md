# Card faces remain readable during artwork loading

Burls reported a blank flop that became readable after an opponent action. His screenshot shows two painted faces and one blank position. The exact original browser failure has not been captured, so this change does not claim to reproduce his full incident.

A reproducible source defect left valid card faces blank for as long as an image request or asynchronous decode remained pending: the existing rank/suit fallback mounted only after both WebP and PNG errors. CardImage now continuously paints its authoritative rank and suit beneath the artwork. Successfully painted artwork covers it; pending, stalled or failed artwork cannot remove the readable face. Invalid card data still renders the explicit unreadable marker rather than guessing a card. The static community-board path now requests artwork eagerly, matching animated faces and reconnect requirements.

No game state, betting, timer, financial behavior or animation timing changes. Five maintained component regressions cover pending artwork, successful and failed artwork, reused slots, two-color identity, invalid input, and static board eager loading. The new pending-face assertions failed before the repair. Focused component and presentation/animation checks passed (198 tests). Chromium and WebKit at 375px painted all three correct flop identities while every image request was held open, without a later game event; actual pixels and source harness retained in task evidence. Original-device reproduction and runtime delivery are reported separately in the task checkpoint.
