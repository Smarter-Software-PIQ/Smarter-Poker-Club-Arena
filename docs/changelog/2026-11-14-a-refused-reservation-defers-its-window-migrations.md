# A refused reservation defers its window migrations to the run that owns the date

On 2026-11-14 three daily reservation runs of `stage-engine-release.yml` reached the 09:30Z cutoff (43557332231, 43577236622, 43580638272): the release controls had changed during the reservation (#10765 election, #10777 booking, #10809), so the two earlier runs were refused with "Release controls changed during reservation; keep serving." and the last one owned the date. All three still named a window-migration source and launched "Install Queued Daily-Maintenance Migrations" at the same instant; the concurrency group ran one and cancelled two with zero steps.

The owner's instruction: refused release runs must not launch competing migration jobs. The cutoff step now records, on a controls-changed refusal, the earliest later active push run of the workflow (`successor`), read once from the run list. When one is visible, `window_source` names no source and that owner installs. When no later run is active, or the list cannot be read (said as `unknown`, never folded into either answer), the step still names protected main at the cutoff, so a refusal never again costs the queued migrations their break (the 2026-11-10 and 2026-11-11 defect that `tests/a-window-migration-does-not-wait-on-engine-release-controls.law.test.ts` pins). The successor is read only on the refusal path; a bound reservation is unchanged.
