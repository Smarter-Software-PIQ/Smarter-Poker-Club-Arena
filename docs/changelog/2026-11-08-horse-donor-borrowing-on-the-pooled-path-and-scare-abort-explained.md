# A Thin Opponent Row Borrows Its Sibling Table Size Again, And The Scare Abort Is Explained

Two findings from the 2026-11-08 capability inventory (HB-CAP-124, 125, 126) on serving release 391f7bc0.

## Donor Borrowing Was Gone From Every Live Decision (HB-CAP-125, 126)

Rule (2026-10-24, 2026-10-25): a new table is not a new player, and a known maniac is a maniac at every table size. A thin or missing exact opponent row borrows the same game's sibling table-size row (short and full; heads-up has none), weighed by Item 12's hand-clock staleness, and the sibling read may corroborate a statistic.

On 391f7bc0 the flush receipts show 1,104,922 `horse_observer_reads_pooled_public` decisions and 0 `opponent_memory_donor_fresh`, `_stale`, `_expired` and 0 `opponent_exploit_corroborated`. The inventory blamed #9693's move to the exact public-memory read. The cause is older and different. Since #8075 every FAST decision reads opponents inside the observer sandbox, and the FAST path refuses the old donor packet (`horse_observer_unscoped_profiles_refused`). The only durable notes a decision sees come from `PooledPublicProfiles.read`, which returned only the exact (variant, mode, size, domain) row. The donor keys `HorseMind.blendDurableRead` looks up were therefore never present in a decision sandbox. #9632's law test drove `HorseMind.importDurableOpponentProfiles` directly, which has no live caller, so it passed while the live path stayed silent. The receipts were not merely unwired. The capability was gone.

The fix restores borrowing on the path decisions take:

- `PooledPublicProfiles.read` also returns the sibling table-size row of the same variant, mode and original speed/ante domain. The donor key carries the domain, so a donor never comes from another domain. The receipt `profiles` now counts the opponents with notes. Its digest covers the donors and is unchanged when there are none.
- The cache keeps each player's own hand clock: the accepted hands the player acted in, with the last eight (availability, count) marks, so an older queued snapshot reads the clock at its own cutoff. Each row records the clock when it was learned (0 for saved bootstrap rows). A donor's staleness is the player's clock at the decision cutoff minus that mark (`computeDonorHandClockStaleness`). It is never a difference of two buckets' hand counts.
- `HorseObserverReads` puts the donor rows into the decision's detached exploit map and their staleness into the new `HorseMindSandbox.donorStaleness`. `runInSandbox` swaps it in and back out, and `snapshotDecisionReads` copies it with the donor row it belongs to.
- `HorseMind.blendDurableRead` takes the staleness from the sandbox when one is present; the import-clock path is otherwise unchanged. On the pooled path, when there is no pooled exact row, the horse's own individual row in that context is the exact evidence that borrows. A thin individual read is therefore blended with the donor and never replaced by it. Receipts `opponent_memory_donor_fresh`, `_stale`, `_expired` fire from the live path. The sibling corroboration (`opponent_exploit_corroborated`) sees the donor row too.

Law: `server/src/engine/horseDecision/aThinOpponentRowBorrowsItsSiblingSize.law.test.ts`. A full-ring maniac is read short-handed through the real observer sandbox. The donor is fresh at learn time and stale after twenty accepted hands that refresh nothing. A newer row makes it fresh again. A lightning-domain row is never borrowed by a table-speed read. The staleness value matches the player's own clock, and an older cutoff reads an older clock.

## The Scare Abort Fires By Design (HB-CAP-124)

`plan_fingerprint_aborted_scare_under_pressure` fired 78 times on 391f7bc0, and the verification expected 0. Neither #9632's changelog nor its law says 0; the changelog names "a scare card while facing a bet" as a withdrawal reason. The expectation came from the measurement side: `activation.sql` listed every plan fingerprint receipt except this one. The branch is legitimately reachable. `barrelPlan` is read whether or not the horse faces a bet, so when a villain leads the scare card into the horse that planned the barrel, the evaluator reports the abort. hand_history for 391f7bc0 shows 39 such spots (a horse that was the last flop aggressor acting on a turn lead) in a single ten-minute window of 5,136 hands. The planned barrel lives only in the not-facing-a-bet branch (`HorseLogic.ts`), so this withdrawal changes nothing the horse does there; it is a receipt only.

No engine code changes for this. `activation.sql` gains the missing row with that meaning. `HorsePlanFingerprintActivation.law.test.ts` gains a case pinning it over 40 seeds: a villain leads the scare turn into the planner, and the receipt fires exactly once. The decision is identical to the `planFingerprint: false` arm, and the off arm leaves no receipt.
