# A solver store is loaded completely before a worker says ready

**Incident (2026-11-19 14:16–14:19 UTC).** Certified candidate `7add8b42c83b` was swapped in under owner window `2026-11-19-owner-no-notice-engine-1030z`. On boot, live Horse decision worker 2's first `gto_postflop` read hit `supabase_timeout`. The loader answered `{ ok: false, count: 0 }`, so worker 2 reported 0 open-node cells while workers 0–7 reported 7,747. `lane.ts` refused readiness ("live horse decision worker 2 loaded a different solver corpus than worker 0"), GameServer stopped, no restart certificate was presented, and the release restored sealed `f3e99378ccbb`. The release receipt recorded "the drain had used the proof and rollback reserve"; the engine log (`engine-20261119T141907Z-…-2730a3dd.log.gz`) shows the boot failure.

**Fix.** The first load on a live decision worker (`gto_charts`, `gto_postflop`) now goes through `loadSolverStoreForBoot` (`server/src/services/solverBootLoad.ts`): a failed or thrown attempt is retried up to three times (1.5 s, 3 s apart). If none completes, boot refuses with a named error (`<store>_boot_load_incomplete_after_3_attempts`). An empty or partial store is never reported as loaded. Periodic refresh, the lane's corpus-equality refusal and the V31 load are unchanged.

**Proof.** `server/src/services/solverBootLoad.test.ts` covers a timed-out first load that recovers, a thrown attempt, refusal after three incomplete attempts, and that both worker boot steps use the boot loader.
