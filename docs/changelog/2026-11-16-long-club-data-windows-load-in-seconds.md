# Long Club Data windows load in seconds (2026-11-16)

**What was wrong.** A Club Data window that reaches back before the union's accounting records begin (2026-09-19) is answered by the older Chicago-day reader. For the union and its clubs that reader was slow on long windows: Midway Union's 93 days took about 31 seconds the first time (about 10 seconds once warm), KINGS CLUB's 93 days never finished inside a minute, and even KINGS's 7 days took 4 to 7 seconds. It added up the whole window twice through an index walk the planner picked because it could not see which clubs it was reading, sorted every row to disk just to count the games, and for KINGS re-read its whole window for every lookup, checking the club list again on every row.

**What changed.** Migration `20261116021023` replaces `ca_club_data_screen_chicago_basis` behind its md5 preimage pin. The router `ca_club_data_screen` is untouched. The reader now looks up the club list once and reads the facts table straight by that list. One pass gives every total and the MTT split, a second, in-memory pass counts the games, and every lookup for the page's rows goes through the table's keys. With the MTT filter on, only MTTs are grouped. Nothing else about the answer changes.

**Proof.** On production (read-only, the old and new readers compared in one snapshot, whole answer minus `generated_at`): Midway Union 93 days identical, 9.9 s to 3.7 s warm (about 31 s cold before); union 30 days identical, 0.5 s to 0.2 s; KINGS 30 days identical, 1.6 s to 0.1 s (6.3 s on a colder run); KINGS 7 days identical, 1.4 s to 0.2 s (4.6 to 7.1 s on colder runs); union 93 days filtered to MTT identical, 10.7 s to 1.2 s; KINGS 93 days identical, 44 s to 1.6 s. The native fixture (`scripts/ci/test-club-data-reads-each-window-once.py`) installs the previous reader, checks its md5 matches production's, installs the new file through its guard and confirms every probe screen is byte for byte the same.

The reader reads the facts table directly. That is the same rows as before only because, since `20261115145150`, both of its former sources read that table as it is; the migration refuses to install if either source has changed.
