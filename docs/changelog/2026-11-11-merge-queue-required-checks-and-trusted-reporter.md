# Merge queue: required checks run on the queued merge group, and a trusted reporter for the money-trigger verdict

Owner approval: Dan, 2026-11-10 18:26 Chicago ("Approve rebuilding for merge queue, including the trusted reporter needed for the money-safety check"), re-confirmed 2026-11-11 00:03 Chicago.

Why: on 2026-11-10 two merges each passed alone and failed together (#10165 after #10265: the required TypeScript Check went red on every PR), and two migrations merged under one version (20261110160345). Both landed on checks that ran against an older main. A merge queue runs every required check on the exact tree that will land.

This change only prepares the queue. It does not turn it on: no ruleset is changed here.

- `ci.yml` and `weekly-refusal-cover.yml` also run on `merge_group` (`checks_requested`). Every job gated on the pull-request event now also runs for the merge group, and every place that used the pull request's base/head SHA uses the merge group's when there is no pull request. The superseded-head check stays pull-request only (a merge group is never superseded). The fixture gate accepts `merge_group` like `pull_request`.
- `Money trigger declaration authority` gets a merge-group path without moving its trust boundary:
  - `money-trigger-merge-group-request.yml` runs on `merge_group` with `permissions: {}`, no secret and no environment. It only exists so its start raises `workflow_run`.
  - `money-trigger-recovery.yml` gains `workflow_run` (`types: [requested]`) and a job `Trusted merge-group verifier execution`. `workflow_run` always runs main's copy of the workflow, so the environment `money-trigger-recovery-trusted` keeps its main-only deployment policy unchanged, and no code from the queued commit runs with the reporter key. The job trusts only GitHub's own `workflow_run` fields: event `merge_group`, this repository, branch `gh-readonly-queue/main/...`, and `head_sha`.
  - It posts the check on the exact merge-group head, verifies the migrations that commit adds over main (`compare main...head`, must be `ahead` with `behind_by 0`, under 300 files, else failure) with the existing trusted verifier, and at finish succeeds only if the group is still live in the queue with that head (GraphQL `mergeQueue`), the migration set read again equals the proof's (path and bytes), the proof names the same head, queue branch and run, the protection read and revocation succeeded, and the verifier passed. Anything unreadable, stale or different is a failure.
- Tests: `tests/money-trigger-merge-group.test.mjs` (13 cases: live group succeeds; left queue, changed or added migration, unreadable set, other head, other branch, PR proof, other run, failed verifier, missing protection all fail; queue liveness fails closed; the job's source and checkout boundary). Pins moved in the same commit, each for the merge_group form only: `tests/money-trigger-ci-caller.test.mjs`, `tests/operations/fixture-required-ci.test.mjs`, `tests/unit/fixtureNativeCi.test.ts`, `tests/unit/requiredCiRunnerRecovery.test.ts` (job and `on` hashes), `tests/a-booking-cannot-start-in-the-past.law.test.ts`, `tests/an-added-club-foreign-key-brings-its-index.test.ts`, `tests/unit/noFixedSizeSourceWindows.test.ts`.
