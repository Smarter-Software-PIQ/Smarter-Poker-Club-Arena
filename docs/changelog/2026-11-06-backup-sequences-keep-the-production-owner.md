# Backup sequences keep the production owner

The isolated backup restored application functions as `postgres` but omitted sequences from owner alignment. Its hand-number sequence stayed owned by `supabase_admin`, so the actual `SECURITY DEFINER` allocator running as `postgres` could not read or advance it. Production grants the service role SELECT only; broadening that grant would conceal the ownership defect.

Owner restoration now includes sequences after their owning tables, preserving standalone, serial and identity sequence ownership without adding grants. The restore receipt records the SHA256 of the owner SQL actually copied into the database container. Refresh selection compares that receipt with the checked-out owner source, and runtime/certification admission compares it with the installed owner source. Missing or changed provenance requires a fresh restore rather than accepting an older incorrectly owned copy.

Focused validation: the existing DR suite checks sequence selection/order, unchanged grants, and missing/mismatched/matching receipt admission. A disposable PostgreSQL 17.11 cluster ran the actual old/new owner SQL and the current hand-number allocator: old ownership produced the observed permission error; corrected ownership passed shared and floor allocation paths under a non-superuser `postgres` role. Serial and identity inserts passed, exact production sequence ACL was retained, service-role direct nextval remained refused, and the private allocator ACL stayed postgres-only. This is isolated source verification; hosted restoration and dealing proof remain separate delivery gates.

The same failed hosted certification exposed two connected reporting defects. Docker log reads now pass the supported epoch timestamp rather than an `@` prefix; unreadable logs still refuse certification. The hosted SSH/tee pipeline is explicitly conditional under bash errexit and pipefail, retaining both its failed verdict and the returned certificate reason even when SSH or tee fails. Existing DR regressions exercise the actual log argument and extracted hosted pipeline for success and both failures.
