# Incident fix audit and class hardening (2026-11-24)

## A repeated cutover refusal cannot hide (CR1)

**Why it broke.** From 2026-11-18 the scheduled cutover kept serving cycle after cycle. The daily miss was paged (`EngineCutoverMissed`), but nothing recorded which gate refused each cycle and nothing failed when the same gate refused again, so three cycles in a row on `backup-lacks-installed-migration` (11-21 22:00, 11-22 01:00, 11-22 04:00 CST) read as weather, not a defect with an owner.

**Fix, inside the existing run.** `stage-engine-release.yml` job `cutover-outcome-record` (needs `detect`, `selection`; admitted scheduled cycles only, attempt 1, no owner window; no new cron or watcher) runs `scripts/ci/cutover-outcome-ledger.py record`. One record per cycle (`selected`, `keep-serving`, `blocked`; a selected cycle is upgraded next cycle to `sealed`, `serving-advanced` or `not-sealed` with gate `receiver-did-not-seal`) with the newest refused candidate's normalised gate, on a rolling ledger carried as the `cutover-outcome-ledger` artifact (90 days, last 240 cycles), seeded from `scripts/ci/cutover-outcome-ledger-seed.json`. The same gate twice in a row fails the job with `::error` naming the gate and opens or comments on one issue `Engine cutover refused twice on the same gate: <gate>` (the red-main detector reads only the latest verdict, and Stage's non-admitted runs go green within minutes). An unreadable ledger is "could not tell" and fails. Detection only; `signal` does not depend on it.

**Backfill (Nov 18-24, 26 cycles, from the archived `daily-engine-selection-*` artifacts).** It would have failed at 11-22 01:00 and 04:00 CST on `backup-lacks-installed-migration`. Other gates seen: `backup-lacks-candidate-migration` (11-19), `no-certified-candidate` (11-20, 11-22 10:00: newer merges, none Backup-certified), `prequalification-unavailable` (11-21), `serving-rollback-rehearsal-unavailable` (11-21 16:00, 11-22 22:00, 11-23 22:00, 11-24 13:00), `backup-holds-migration-production-lacks` (11-23). The selection labels any candidate whose Backup evidence lacks the rehearsal fields as `serving rollback rehearsal unavailable`, including the 11-24 13:00 hand-gap refusal; the record keeps the selection's own label.

**Proof.** `scripts/ci/test-cutover-outcome-ledger.py` (17 cases: two identical refusals fail; a seal, a selection, a different gate or nothing-to-ship resets; a receiver that did not seal twice fails one cycle late; the same cycle counts once; unreadable inputs exit 2; the real refusal strings classify; the seed is the backfill; the job's wiring). It runs in the required `Incident class proofs` check.

Owner orders: 2026-11-17 13:50 Chicago and 2026-11-24 01:23 Chicago ("verify every fix was hard coded and fixed without patches, go back through each one, figure out why it broke and how, then harden each so it can't break or regress again"). ## Method

- **Owning source**: read each merged diff; the change must sit in the function, schema, workflow or engine code that owns the behaviour, not in a wrapper, a cron or a data patch.
- **Fails before / passes after**: each regression test was copied from its merge commit into a detached worktree at the merge commit's parent (`M^1`) and at the merge commit (`M`), and run there (`/Volumes/SmarterWork/agent-work/extreme-capacity/z1-audit-harden-20261124/failbefore.sh`, re-runs on SSD1 in `.../shared-capacity/z1-audit-harden-20261124/fb2.sh` and `fb3.sh`). "Fails before" means the parent run exits non-zero for the fixed behaviour; a missing-file refusal is recorded as such.
- **Required**: ruleset 21163380 required contexts on 2026-11-24 were TypeScript Check, Client Unit Tests (vitest), Server Engine (typecheck + tests), Production Build, CSS Beat E2E, Money trigger declaration authority, Weekly refusal receipt cover, Window migrations install against production's schema, and Production's DDL guards pass before merge. `tests/**` law tests run under the required Client Unit Tests (vitest); `server/src/**` tests under the required Server Engine. Native PostgreSQL proofs in path-filtered workflows were **not** required.

## Retention prune page cost (pg_cron job 117, 2026-11-24)

**Symptom.** `public.sp_prune_hand_history` ran 15.9–19.6 s per run on average (max 40.4 s), back to back every 10 seconds, from 06:00 to 13:00 UTC while the pass caught up from 2026-11-15 to the 8-day frontier. It was one of the sources of the DatabaseRepliesLost saturation firings.

**Dominant step, measured on production.** Read-only timing in a rolled-back `DO` block over frontier hands that are 8 days old:

- `public.fn_pnl_cash_hand_evidence` costs about 26 ms per hand.
- Each doomed horse hand reaches it up to three times:
  - `smarter_private.horse_cash_retention_accounting_ready`, the candidate guard
  - `smarter_private.compact_horse_settlement_keys`
  - `smarter_private.compact_horse_cash_play_contents`
- 200 hands × 3 calls × 26 ms comes to about 15.6 s of the roughly 17 s page.

Inside the evidence function, `smarter_private.original_treasury_participant_gift` was the largest piece: about 10 ms per hand, or 2 ms per participant.

The other pieces measured per 30 hands:

| Piece                      | Time per 30 hands |
| -------------------------- | ----------------- |
| Funding lineage            | 0.12 s            |
| Settlement original result | 0.04 s            |
| Atomic match               | 0.03 s            |
| Initial-receipt checks     | 0.03 s            |
| Receipt and request reads  | 0.03 s            |

The scan, the citations and the anti-joins were already under 60 ms. Foreign-key cascades were ruled out: only two foreign keys reference `hand_history`, and both of their tables are empty.

**Why it broke.** The gift lookup ran the full byte-exact proof, `original_treasury_gift_evidence`, for every gift witness. Only afterwards did it compare each proof's occupancy with the participant's. That cost:

- grows with every witness ever admitted
- is paid for every participant of every hand
- is paid up to three times per pruned hand

The proof derives its `occupancy_id` from the witness's own `source#>>'{seat_event,after_row,occupancy_id}'`. The table already allows only one gift per occupancy (`original_treasury_gift_occupancy_once`). So almost all of that work could never change the answer.

**Source fix: migration `20261124191500_a_treasury_gift_is_looked_up_by_its_own_occupancy`.** It is a guarded single-anchor amendment of the live definition.

- **What it skips.** A witness whose source occupancy is canonical uuid text and differs from the participant's. Such a witness can never match.
- **What still runs in full.** A witness whose occupancy is non-canonical text is still proven.
- **Unchanged:**
  - retention policy
  - deletion totals
  - every money-evidence guard, filter and exactly-one rule
  - the exception handler

**Equivalence proved three ways:**

1. **Production, read-only:**
   - 539 participants of 120 frontier hands showed 0 differences.
   - Each of the 4 witnesses' own chairs returned the same proof.
   - Time for those 539 calls fell from 0.916 s to 0.070 s.
2. **Native PostgreSQL 17 copy:** the live definition verbatim, plus a stand-in proof of the same shape, run on 454 cases.
   - Cases covered:
     - every own chair, including upper-case, braced and unhyphenated occupancies
     - foreign chairs
     - wrong table
     - late capture
     - missing occupancy
     - malformed join time
   - Results before and after:

     | Measure         | Before | After |
     | --------------- | ------ | ----- |
     | Proofs returned | 123    | 123   |
     | Error outcomes  | 20     | 20    |
     | Differences     | —      | 0     |
     | Proof calls     | 54,027 | 1,544 |

   - Re-applying the migration is a no-op.

3. **The pin moves with the body.** `smarter_private.original_inventory_proof_sources_match()` pins this function's md5 (`95b9a25f9a422bb7d8df115f86bc5993` on 2026-11-24). The first push was refused by the hosted DDL-guard rehearsal (applier stale-pin guard). The migration now moves that one pin in the same transaction. It asserts the list answers TRUE again, the generation keeps its `original-inventory-245-v1` shape and no installed function still names either old md5. The generation value rotates because it hashes the list function's own body, as it did with 20261123202500. Nothing pins the list function itself.
4. **The migration's own probe:**
   - Every admitted witness still proves its own chair.
   - A random foreign occupancy finds nothing.

**Class hardening.** `tests/a-treasury-gift-is-looked-up-by-its-own-occupancy.law.test.ts` and its `docs/laws.d` entry:

- fail on the old shape, because the migration and its prefilter are required
- fail if any later migration redefines the lookup without the prefilter
